# Mitra Accessibility Baseline

The hard target for every screen, every component, every shipped version of Mitra. Accessibility is cheaper to bake in than to retrofit — buttons sized correctly from day one cost nothing; buttons resized in V4 cost a sprint per screen.

**Audience focus**: older Indian users, low-vision users, one-handed thumb operators (common on 6.5"+ phones), users with system font scale at 130-200%, screen-reader users via TalkBack, users in RTL contexts (Urdu in future regional rollouts), keyboard-and-D-pad users on tablets and foldables.

**Implication for design**: every choice in tokens.md, screens.md, action-cards.md, permissions.md, and onboarding.md is checked against the targets in this file. Where there is conflict, accessibility wins.

---

## 1. Hard targets

| Target | Requirement | Why |
|---|---|---|
| **WCAG 2.2 Level AA** | All text, focus, and interactive contrast meets 4.5:1 for normal text, 3:1 for large text and UI components | Baseline regulatory and inclusive-design standard |
| **TalkBack reachable + readable** | Every interactive element has a `contentDescription` or `Modifier.semantics`; every screen is fully navigable via swipe gestures only | Blind / low-vision users rely on TalkBack |
| **200% font scale survivable** | Layouts do not break, clip, or hide content when `Settings.System.FONT_SCALE = 2.0` | India has high adoption of system font scaling among older users |
| **4.5:1 minimum text contrast** | Stricter than WCAG AA's 3:1 for large text — Mitra uses 4.5:1 for everything ≥ 14sp; 7:1 (AAA) for `Body` ≥ 16sp | Covers users with mild visual impairment without requiring a high-contrast theme |
| **48dp minimum touch targets** | Every tappable element has a hit area of 48dp × 48dp, even if visually smaller | Material Design minimum; thumb-reach reality on large phones |
| **RTL-safe** | All `start`/`end` paddings and alignments use `Modifier.padding(start = ..., end = ...)`, never `left`/`right`. All directional iconography (arrows) is `LocaleHelper.autoMirrored = true` | Future Urdu support; current Arabic-numeral mixed text rendering |
| **Keyboard navigable** | Every screen has a defined focus order; every interactive element is reachable via Tab / D-pad | Foldable / tablet split-screen with external keyboard; future Chromebook running Android apps |
| **Reduced motion respected** | When `Settings.Global.ANIMATOR_DURATION_SCALE = 0` or system "Remove animations" is on, motion tokens collapse to instant (motionFast becomes 0ms; bouncy easings become linear; decorative animations are skipped entirely) | Vestibular sensitivity, motion sickness, low-end devices |
| **No colour-only state cues** | Every state distinguished by colour ALSO carries a glyph, label, or position cue | Colour-blind users; deuteranopia is ~5% of male population in India |

## 2. Per-component checklist

Each component below has a specific accessibility contract. PRs adding or changing these components run an instrumentation test that checks the contract.

### 2.1 Input bar (Chat screen)

- **TalkBack label**: "Message Mitra. Editable text field."
- **Send button label**: "Send" (not just an icon).
- **Mic button label**: "Voice input — not available in this version" (until M4); "Hold to record" (post-M4).
- **Focus order**: text field → mic → send.
- **Min size**: text field min height 48dp; send and mic each 48dp × 48dp.
- **Font scale**: text field expands vertically up to 4 lines at 200% scale; beyond 4 lines it scrolls internally rather than blocking the screen.
- **Contrast**: placeholder text ("Ask Mitra anything") at `onSurfaceVariant` meets 4.5:1 on `surfaceVariant` background.
- **Keyboard**: Enter sends; Shift-Enter inserts newline; Tab moves focus to send.

### 2.2 Chat bubble

- **TalkBack reading order**: `[role] [content] [timestamp] [state if any]`. Example: "Mitra. Alarm set for 7 AM tomorrow. Two seconds ago."
- **No `Modifier.clickable` on the bubble itself** unless the bubble has an action (long-press for copy, etc.). Avoid accidental tap targets.
- **Long-press to copy**: announced via `Modifier.semantics { onLongClick("Copy message") }`.
- **State pills (e.g., "Sent", "Failed")**: announced as part of the bubble content, not as a separate node.

### 2.3 ActionCard — Silent / Ambient ribbon (Mode A)

- **TalkBack label**: full sentence. "Flashlight on. Just now." Not "Flashlight icon. Done state."
- **Live region**: ribbon is announced via `LiveRegion.Polite` when it appears, so screen-reader users hear about ambient actions.
- **Failure state**: announced with priority — `LiveRegion.Assertive` — because the failure needs attention.
- **Visual fade-out timing**: respects reduced-motion (instant appear, instant remove).
- **Compacted state in chat stream**: behaves as a chat-bubble for a11y purposes.

### 2.4 ActionCard — Toast variant (Mode B)

- **TalkBack reading order**: "Alarm set for 7 AM. Tomorrow, weekday. Undo button. Three seconds remaining."
- **Undo countdown**: announced once as remaining time when the card lands; not re-announced as it ticks (would be noisy).
- **Undo button**: minimum 48dp hit target.
- **Failure state**: state pill change announced; recovery affordances ("Try again", "Edit", "Dismiss") each labelled.

### 2.5 ActionCard — Modal variant (Mode C — ConfirmationGate)

- **Focus trap**: when the modal opens, focus moves to the headline; Tab order cycles within the modal until dismissed.
- **TalkBack announces on open**: "Confirm dialog. Send SMS. To Priya. Quote running late unquote. This sends an SMS. SMS counts toward your carrier plan. Two buttons: Cancel, Send."
- **Confirm button**: announced with its action verb, not just "OK". "Send" or "Call" or "Delete".
- **Tap-outside dismissal**: announced as available; tap-outside reads as "Cancel" for a11y purposes.
- **5-min suppression checkbox**: explicitly labelled "Don't ask again for this action in the next five minutes. Unchecked." TalkBack toggle behaviour standard.
- **No `running` state without explanation**: when buttons disable, TalkBack hears "Running" so users know the system is working, not stuck.

### 2.6 ConfirmationModal (in screens.md, hosted by Chat ViewModel)

Same as Mode C ActionCard. The two are the same component in practice.

### 2.7 Settings row

- **TalkBack reading order**: `[icon-label] [setting name] [current value or state]`. Example: "Phone access. Granted." or "Theme. System default."
- **Toggle rows**: standard switch a11y — "Setting name. On." or "Setting name. Off."
- **Disabled rows** (cooldown active): announced as "Phone access. Not now. Available to re-enable in 23 hours. Or tap re-enable now button."
- **Section headers**: have a `Modifier.semantics { heading() }` so screen-reader users can navigate by heading.
- **Min row height**: 56dp regardless of font scale (the row scales beyond 56dp at higher scales but never collapses below).

### 2.8 PermissionRequest / PermissionBounce screens

- **TalkBack reading on open**: announces the why-needed copy as the first node after the screen title.
- **3-step / 4-step illustrations**: each step has an alt label. "Step one of three. Settings page." TalkBack walks the user through the visual flow.
- **Primary CTA "Open settings"**: announced as "Opens device settings. You will return here automatically."
- **Bounce return detection**: when the user returns from system settings, a transient announcement is made: "Permission granted." or "Permission still off."
- **"Not now" / Skip CTAs**: never hidden, always reachable; announced as "Skip for now. You can grant access later from Settings."

### 2.9 Model download screen

- **Progress bar**: `Modifier.progressSemantics(value = progress, valueRange = 0f..1f)` so TalkBack reads percentage on demand and announces milestones (25%, 50%, 75%) automatically via polite live region.
- **Byte counter** ("1.43 GB of 2.59 GB"): does not flood TalkBack — re-announced only every 30 seconds or on user request, not on every byte tick.
- **ETA**: announced once when stable (after 5 seconds of consistent prediction), then only when it changes by ≥1 minute.
- **Pause / Resume / Cancel**: standard button labels with action verbs.
- **Failure / hash-mismatch**: assertive live region; immediately announced with recovery affordance.

### 2.10 Audit history rows

- **TalkBack reading order**: `[action type] [target] [timestamp]`. Example: "Tool: Flashlight turned on. Just now." or "Permission grant: Phone access. Today at 9:42 AM."
- **Filter chips**: standard chip a11y; selected state announced ("Today filter, selected").
- **Empty state**: announced as a region with its single message ("Nothing to log yet. Every action Mitra takes will appear here.").
- **Export button**: announced as "Export audit log to file."
- **Clear button**: announced as "Clear all audit history. Opens confirmation."

## 3. Per-screen a11y test plan

For each screen, the following manual + automated tests run before any release. Automated tests live in instrumented test suites; manual tests are documented in `docs/qa/a11y-manual.md` for human testers.

### Manual test recipe (run once per screen per release)

1. **Open the screen with TalkBack on.** Listen to the announcement on entry. It should be informative without being overwhelming.
2. **Navigate every element via swipe-right.** All interactive elements must be reachable; no element should be silent or labelled as "unlabelled image".
3. **Set system font scale to 200%.** Scroll the screen. No content clipping, no horizontal scroll, no buttons cut off.
4. **Set system display size to "Largest".** Same as font scale — no breaks.
5. **Enable "Remove animations" in Developer Options.** Every animation should be instant; no functionality should be lost.
6. **Use the screen with one thumb.** Every primary action must be reachable from the bottom 60% of the screen. Top app bar icons can be top-right but must have alternatives.
7. **Switch to dark mode.** Verify contrast holds; verify no element disappears against the warm-dark background.
8. **Set system to RTL (developer setting: "Force RTL layout direction").** Layouts mirror correctly; arrows point the right way; text remains readable.
9. **Connect a Bluetooth keyboard and Tab through the screen.** Focus order is logical; focus indicator is visible; every interactive element receives focus.
10. **Toggle "Colour correction" in Accessibility settings (Deuteranopia).** All state cues remain understandable; no information lost when colour is filtered.

### Automated test coverage

- **Compose `Modifier.testTag`** on every interactive element, used by both instrumentation tests and a11y assertion tests.
- **`accessibility-test-framework`** integration that scans for: missing content descriptions, touch targets < 48dp, contrast failures (via Espresso AccessibilityChecks).
- **Snapshot tests at 100% and 200% font scale** for every screen — visual regression catches layout breaks before merge.
- **TalkBack reading order assertion** for top three screens (Chat, ConfirmationModal, ModelDownload) — uses a custom test rule that verifies the semantic tree order.
- **CI gate**: PRs that fail accessibility assertion tests cannot merge. PRs that fail visual snapshot tests require a screenshot review and explicit override.

## 4. Voice-only and screen-only fallbacks

Two extreme users to design for:

### Voice-only user (post-M4)
- Pure screen-reader user who cannot see the screen at all.
- Every ActionCard must be announceable as a complete sentence.
- ConfirmationModal must read its full state on focus; buttons must have action-verb labels, never "OK".
- Suggestion chips must be announced as a list ("Six suggestions available") with each chip individually focusable.
- No critical information exists only in colour, position, or icon — every cue has a text or label equivalent.

### Screen-only user (no audio output)
- Hard-of-hearing or deaf user, or user in a quiet environment with sound off, or user with broken speakers.
- All TTS in M4 must have a visual transcript equivalent.
- Voice mode (M4) is opt-in; the keyboard remains the equal path.
- Notifications use vibration patterns (mapped in tokens.md §7), never audio cues alone.
- Action card state changes are always visually distinguishable; the haptic is supplementary, not primary.

### Both-impaired user
- Braille display via TalkBack works — content descriptions must render meaningfully to a Braille reader (no decorative emoji, no unicode tricks).
- All visual flow has a non-visual equivalent.

## 5. The five most common Compose a11y bugs to guard against

These come up on every Compose codebase. Each has a specific guard.

### Bug 1 — Decorative `Image` without `contentDescription = null`
- **Symptom**: TalkBack announces "Image" for every illustration.
- **Guard**: a lint rule (`MissingContentDescription`) flags any `Image` or `Icon` Composable without an explicit `contentDescription` — either a string for meaningful images or `null` for decorative ones.

### Bug 2 — Clickable `Box` without `Modifier.semantics { role = Role.Button }`
- **Symptom**: TalkBack reads the click target as "Double tap to activate" without saying what it is.
- **Guard**: a custom Detekt rule flags `Modifier.clickable` not preceded by a `.semantics { ... }` block within the same Composable.

### Bug 3 — Custom `state pill` colour without text equivalent
- **Symptom**: "FAILED" state looks red but TalkBack reads "Action card" with no state info.
- **Guard**: every ActionCard state has a `stateDescription` semantics property set from the state pill text. Tested in `ActionCardA11yTest.kt`.

### Bug 4 — Animations bypassing reduced-motion
- **Symptom**: User has "Remove animations" enabled but ActionCard still slides in.
- **Guard**: every animation in `ui/motion/` reads `LocalReduceMotion.current` and collapses to instant if true. A test asserts no `animateAsState` or `AnimatedContent` call exists without consulting this LocalComposition.

### Bug 5 — Focus traps that don't release
- **Symptom**: Modal opens, focus is trapped inside; user dismisses; focus stays in the dismissed modal's slot; next Tab goes nowhere.
- **Guard**: every modal-opening Composable uses `BackHandler` and explicitly returns focus to the invoking element on dismissal. Tested in `ModalFocusTest.kt`.

## 6. Specific contrast verification (for tokens.md palette)

Cross-reference of tokens.md colour pairs against WCAG 2.2 AA. Both palettes must verify before V1 ships.

| Pair | Light ratio | Light pass? | Dark ratio | Dark pass? |
|---|---|---|---|---|
| `onSurface` on `bg` | 14.8:1 | AAA ✓ | 14.5:1 | AAA ✓ |
| `onSurfaceVariant` on `bg` | 7.1:1 | AAA ✓ | 7.4:1 | AAA ✓ |
| `onSurfaceVariant` on `surfaceVariant` | 6.2:1 | AA ✓ | 5.8:1 | AA ✓ |
| `onPrimary` (white) on `primary` (light) | 4.7:1 | AA ✓ | — | — |
| `onPrimary` (dark) on `primary` (dark) | — | — | 5.1:1 | AA ✓ |
| White text on `success` | 4.9:1 | AA ✓ | 8.2:1 (text on bg) | AAA ✓ |
| White text on `warning` | 5.4:1 | AA ✓ | 9.7:1 (text on bg) | AAA ✓ |
| White text on `danger` | 6.3:1 | AA ✓ | 6.5:1 (text on bg) | AA ✓ |
| White text on `info` | 6.7:1 | AA ✓ | 7.8:1 (text on bg) | AAA ✓ |
| `outline` border on `surface` | 2.1:1 | UI-component pass (3:1 only required for state-cue borders, not decorative dividers) | 2.4:1 | UI pass |

**Verify before ship**: run every pair through `androidx.core.graphics.ColorUtils.calculateContrast(fg, bg)` in a unit test. The test is `TokensContrastTest.kt`; it fails CI if any pair drops below its required ratio after a token edit.

## 7. Internationalisation a11y notes

### Hindi rendering (Devanagari script)
- Per voice.md §5, Devanagari needs +1sp on Body when active locale is Hindi. This is an a11y concern as much as a typography one — Devanagari glyphs lose clarity at 16sp vs Latin glyphs.
- Line height for Devanagari runs 10% taller than Latin; `lineHeight = 24sp` for Body may need to be `26sp` in Hindi. Verify on Pixel and on Samsung (different Devanagari renderers).
- Number rendering: by default Android uses Devanagari numerals in Hindi locale. For technical strings (byte counts, percentages, timestamps), force Latin numerals via `Locale.Builder().setLanguageTag("en-IN")` for the number formatting only — Indian users overwhelmingly read Latin numerals in tech contexts.

### Future Tamil / Telugu rendering
- Tamil and Telugu scripts have tall glyphs with descenders that need more line-height headroom. Body line-height in those locales may need to be 28sp for the same 16sp text size.
- Test on a low-DPI device — these scripts degrade faster than Latin at lower pixel densities.

### RTL preparedness (Urdu, future)
- All directional iconography in tokens.md and action-cards.md uses `automirrored` Material Symbols.
- Padding tokens use `start` / `end`, never `left` / `right`. Audit on every PR.

## 8. Out of scope for V1

- **High-contrast theme** as a separate third theme — the dark warm palette already meets AAA for most text on most surfaces; a high-contrast theme is V2 if user feedback demands it.
- **Font replacement** for dyslexia (OpenDyslexic, etc.) — Inter is highly legible but a font picker is V2.
- **Custom haptic intensity per user** — V1 has a single "Reduce haptics" toggle (on/off). Granular control is V2.
- **Switch Control / external switch accessibility** — V1 supports the OS-level switch access via standard Compose focus + click semantics; no Mitra-specific switch UI is built.
- **Voice control of the app via TalkBack actions** — V1 standard TalkBack actions work; no custom voice-control surface is built.

## 9. Ownership

This file is owned by whoever is reviewing the PR that touches the most-used screens (Chat, ConfirmationModal, ModelDownload). Every quarter, a manual a11y pass is run by a TalkBack user from the community; their findings are filed as GitHub issues with the `a11y` label and are blocker-class for the next release.
